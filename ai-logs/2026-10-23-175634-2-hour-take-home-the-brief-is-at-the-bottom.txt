  I chose a Stack with header links over the template's tabs because it means
  fewer moving parts.

  src/services/
  - config.ts: API_BASE_URL, the one place it is defined
  - types.ts: typed shapes for the API payloads and the error body
  - api-error.ts: ApiError (status, code, field, retryAfterMs), NetworkError,
    isRetryable, retryDelay
  - decode.ts: small hand-written runtime checks that turn the unknown JSON into
    typed objects. Zod isn't allowed, and res.json() returns any.
  - api-client.ts: fetch wrapper that adds the auth header, passes on the abort
    signal and maps errors
  - query-client.ts: default retry policy (retry only retryable errors; wait
    retryAfterMs on 429)
  - query-keys.ts, balances.ts, claim-options.ts, claims.ts (create and poll),
    activity.ts (infinite query)

  src/utils/ (pure code, unit tested)
  - amount.ts: format check, parseUnits(str, decimals) to bigint, formatUnits
  - claim-validation.ts: validateClaimAmount returns { ok, units } or a typed
    error code
  - usd.ts: exact amount × price with bigint, the total, formatting to cents
  - idempotency.ts: makes a UUID with crypto.randomUUID, falling back to
    getRandomValues. randomUUID only exists on https or localhost, so it is
    missing when you test on a phone over the LAN.
  - time.ts: "updated 12 s ago"
  - __tests__/*.test.ts

  src/hooks/: use-token.tsx (context plus AsyncStorage, which uses localStorage
  on web), use-now.ts (ticking clock), use-claim-draft.ts (form state plus one
  idempotency key per body)

  src/components/: screen.tsx (phone-width container), query-states.tsx
  (Loading, Error with retry, Empty), button.tsx, balance-row.tsx,
  total-card.tsx, freshness-label.tsx, asset-picker.tsx, destination-picker.tsx,
  amount-input.tsx, claim-summary.tsx, claim-status-card.tsx, activity-row.tsx

  Build order (one step per review)

  0. Clean-up: remove template demo files (explore, splash overlay, badges), add
     the Jest preset and a test script. No new dependencies.
  1. Money utils and tests: everything else depends on these, and doing them
     first covers the Tests item early.
  2. API layer: config, types, errors, decoders, client, query client.
  3. Token gate: token screen, saving it, changing it, clearing the cache,
     handling 401.
  4. Home: balances with loading, error, empty, refresh and freshness.
  5. Claim: form, review, submit with idempotency.
  6. Claim tracking: polling until the claim completes or fails, then refetching
     balances.
  7. Check pass: 390 px layout, lint, tsc, deploy.
  8. Activity: if there is time.

  Questions

  1. Total in USD. What should it include? I'd sum available + pending +
     claiming (everything earned but not yet received) and show "available" as
     its own line. The other option is to count only available.
  2. USD rounding. I'd round down to the cent so we never overstate money. Is
     that OK?
  3. Comma as decimal separator. Many phone keyboards in Europe and Georgia show
     ,. I'd turn , into . before validating, and stay strict otherwise. Is that
     OK?
  4. Deploy target. app.json has web.output: "server". Are you deploying with
     EAS Hosting (eas deploy), or should I switch to "single" or "static" for a
     plain static host?
  5. Idempotency key after a reload. I plan to keep it in memory, so a retry in
     the same session is safe. If the response is lost and the user reloads, a
     new key could create a second claim. I could save the pending key in
     sessionStorage until the claim succeeds. That's extra code, but it's real
     money. Should I?
  6. AsyncStorage. You've staged @react-native-async-storage/async-storage. Is
     it OK to use it for the token, or would you prefer plain localStorage,
     since we only target web?
  7. Template clean-up. Can I delete the demo components (explore.tsx, animated
     icon, splash overlay, web badge, hint row, collapsible, external link)? I'd
     keep themed-text, themed-view and the theme constants.
  8. Activity sort order. The brief says to show accruals, reversals and claims.
     I'll show them in one list, newest first, as the API returns them. No
     filter tabs unless you ask.

  Decisions worth checking
  - Payloads are checked at runtime. res.json() is typed any, so every body goes
    through a decoder before the app sees it. Balance amounts are also checked
    against their asset's decimals. That means the money utils can trust them,
    and an amount sent as a JSON number is rejected. A malformed success body
    doesn't retry, because retrying won't fix it.
  - Retry policy.
    - Retried: network errors, 429 and any 5xx (including 502s from a proxy).
    - Never retried: 400, 401, 404 and 409.
    - 429 waits the server's retryAfterMs, or the Retry-After header. Everything
      else backs off 1 s, 2 s, 4 s, capped at 8 s.
  - Own timeout. The browser has no fetch timeout, so a stalled connection would
    spin forever. After 30 s it becomes a retryable NetworkError; for a POST
    that means "outcome unknown", which the idempotency key makes safe to retry.
  - A dropped connection mid-body counts as a network error. It's then retryable
    instead of being treated as bad data. That matters when a claim POST is cut
    off halfway.
  - Error bodies that aren't JSON (for example a proxy's HTML 502) get an error
    code based on the HTTP status.
  - Cancellation passes through untouched. When TanStack cancels a request, the
    abort error is rethrown as-is so TanStack can discard it, rather than
    turning into a NetworkError.
  - Cache keys don't include the token. The whole cache will be cleared when the
    token changes (step 3), so the secret stays out of the keys.

⏺ Both complaints come from the same gap: for up to 15 s after a claim, the
  balance on screen is a snapshot taken before the claim.

  What causes each complaint
  - "Didn't change, so I claimed again." The claimed amount leaves available on
    the server immediately, but the next snapshot can be up to 15 s away.
    Meanwhile Home shows the old numbers. A second claim is a new submission
    with a new idempotency key, so the server accepts it as a real second claim,
    as long as enough is live-available.
  - "Dropped, then jumped back up." Three possible causes:
    a. The app subtracts the claim locally, then a refetch returns a snapshot
       taken before the claim and overwrites it.
    b. The claim failed, and the server returned the amount to available. That's
       correct, but nothing explained it.
    c. Responses arrive out of order, so an older snapshot replaces a newer one.

  Approach A: subtract the claim on screen until the server catches up
  - Keep a list of claims created on this device (id, asset, amount, createdAt).
    While a snapshot's asOf is older than a claim's createdAt, show available −
    amount and claiming + amount. Once a snapshot with asOf ≥ createdAt
    arrives, drop the adjustment and trust the server. If the claim fails, drop
    it too.
  - Good: the balance changes the moment you claim, which tackles complaint 1
    directly. Comparing against createdAt instead of "the next refetch" avoids
    the drop-then-jump of cause 1.
  - Cost:
    - The most logic of the three, and it touches money display.
    - It depends on asOf ≥ createdAt meaning "this snapshot includes the claim".
      If that's wrong, the amount is counted twice or flickers.
    - The list has to survive a reload. Claims made in another tab or on another
      device aren't covered.
    - Every bit of this math needs tests.

  Approach B: leave the numbers alone and make the in-flight claim obvious
  - Snapshots stay the only source of numbers. Home shows a banner such as
    "Claim of 0.5 ETH processing — balances update within 15 s", with a link to
    the claim's status, and a badge on that asset. Starting a second claim for
    an asset with one in flight shows a warning to confirm. When a claim fails,
    show "Claim failed — 0.5 ETH returned to available", so the jump back has an
    explanation.
  - Good:
    - Simple, and never shows a number the server didn't send.
    - The warning blocks the double claim at the moment it would happen.
    - Explains cause 2, the legitimate jump back.
  - Cost: for up to 15 s the balance still visibly hasn't changed. It relies on
    the user reading the banner, so it addresses the confusion, not the stale
    number itself.

  Approach C: never go backwards, and wait for a snapshot that includes the
  claim
  - Two rules. First, never replace a snapshot with one whose asOf is older,
    which fixes cause 3. Second, after a claim, keep showing the current numbers
    marked "Updating…", poll faster (about every 3 s) until a snapshot with
    asOf ≥ claim.createdAt arrives, then show it.
  - Good:
    - Numbers only ever move forward, and there's no client-side money math.
    - The "Updating…" state tells the user the balance is about to change.
  - Cost:
    - Up to 15 s of a visible "Updating…" state.
    - More requests while waiting, which uses some of the rate limit.
    - It doesn't block a second claim by itself.
    - It rests on the same asOf/createdAt assumption as A, but if that
      assumption is wrong you get a longer wait rather than a wrong number.

  Side by side

  ┌────────────────────┬───────────────┬────────────────┬──────────────────┐
  │                    │ A: subtract   │    B: show     │ C: forward-only  │
  │                    │   on screen   │   in-flight    │      + wait      │
  │                    │               │     claim      │                  │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Balance reacts     │ Yes           │ No (banner     │ Shows            │
  │ immediately        │               │ instead)       │ "Updating…"      │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Numbers only from  │ No            │ Yes            │ Yes              │
  │ the server         │               │                │                  │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Stops the "claimed │ Mostly        │ Yes (warning)  │ Partly           │
  │  again" case       │               │                │                  │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Stops the "jumped  │ Yes, if the   │ Explains       │ Yes              │
  │ back" case         │ rule holds    │ failures       │                  │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Complexity / risk  │ High          │ Low            │ Medium           │
  ├────────────────────┼───────────────┼────────────────┼──────────────────┤
  │ Extra requests     │ No            │ No             │ Yes, while       │
  │                    │               │                │ waiting          │
  └────────────────────┴───────────────┴────────────────┴──────────────────┘

  Combining them: the approaches overlap. The forward-only rule from C and the
  failure message from B are cheap, and fit with A or B. The double-claim
  warning from B fits with any of them.

  Before choosing A or C: both depend on asOf ≥ createdAt meaning "the snapshot
  includes the claim". The docs suggest it ("a claim you just created may not
  show up until the next one"), but I'd want to see it with your token: create
  one claim, then poll balances and watch for the first asOf after createdAt.

  Which approach do you want?

  Decisions worth checking
  - A refused claim clears the saved draft. Only a refusal from the server (400,
    401, 404, 409) proves nothing was created, so only that clears it. A
    network error, 429, 5xx or 504 keeps the draft, and the button becomes "Try
    again". The message says the claim may already exist and that retrying is
    safe.
  - Offline: TanStack pauses the mutation and sends it when the connection is
    back. The review step says so.
  - "Discard" on the banner forgets the saved key. If that claim did reach the
    server, a new claim with a new key would be a real second claim. I kept
    Discard so users aren't stuck with the banner; say if you'd rather only
    allow resending.
